# Security syntax: opaque inputs and platform contracts

Reviewed 2026-09-30 against SQL Server 2025 (17.x), compatibility 170. The companion `security-inventory.json` distinguishes structured syntax from partial coverage. Source comparison and manual inspection were followed by user-triggered parser/convention validation; see [validation-report.md](validation-report.md). No SQL Server execution or Studio integration was performed.

These contracts supplement `placeholders.md`. A placeholder is not permission to concatenate arbitrary SQL. All quoted lowercase values below stand for string contents: the consumer supplies the surrounding quotes shown in SNF and doubles embedded single quotes. Binary inputs are complete hexadecimal SQL binary constants. Secrets and key material must not be included in generated examples, diagnostics or logs by default. These are syntax/data contracts, not a permission system or execution policy.

## Names and binding

- `name`: primary object identifier appropriate to that statement. Most security objects are single-part database- or server-scoped names. Security policies may be schema-qualified; modules being signed may be schema-qualified. `CREATE USER`/`CREATE LOGIN` must bind names to the selected principal kind; Windows names include the required domain component and escaping. Temporary symmetric key names may start with exactly one `#` and cannot use an EKM provider
- `database_name`, `schema_name`, `login_name`, `new_login_name`, `new_user_name`, `new_role_name`, `certificate_name`, `asymmetric_key_name`, `symmetric_key_name`, `credential_name`, `provider_name`, `assembly_name`, `column_master_key_name`, `audit_name`, `new_audit_name`: typed identifiers, not expressions or SQL fragments. Resolve in the statement's database/server scope and quote each identifier component. Certificate/asymmetric-key login sources must exist in `master`; TDE encryptors must be server-accessible encryptors in `master`
- `database_principal`, `server_principal`, `principal_name`, `grantor_principal`: one resolved principal of the permitted kind for the selected scope. Do not mix server logins with database users. Some ownership targets reject groups/roles; `SCHEMA OWNER` applies only where the securable is schema-contained. Permission inheritance, grant authority and dependency effects are engine checks
- The quoted `principal_name` in `EXECUTE AS` is an impersonation principal string, not an identifier token. The unquoted `principal_name` in GRANT/DENY/REVOKE and ownership syntax is an identifier
- `object_name`, `system_object_name`, `securable_name`, `column_name`: resolved objects/columns of the selected permission or audit class. Object names may be schema-qualified. A system object must be an eligible system object in the current database and only the documented SELECT/EXECUTE subset is represented. A permission class is not an arbitrary type name
- `table_name` and `predicate_function_name`: the RLS target table and inline table-valued function, normally schema-qualified. Do not substitute a scalar function, query, procedure, or arbitrary FROM expression. Native-compilation and schema-binding requirements are checked after binding
- `classified_column_name`: exactly `table.column` or `schema.table.column`; do not accept a wildcard, a table by itself, a variable, or a general expression
- `language_name`: a server-supported default-language name or alias with SQL-appropriate quoting. `language_value`: a contained-user language name/alias or numeric LCID; `NONE` is represented separately. Validate against the server language catalog rather than treating this as arbitrary SQL

## String, binary and scalar values

- `password`, `old_password`, `encryption_password`, `decryption_password`: string contents subject to the selected operation's password length/policy rules. A login password hash is a distinct input, never a password string with a HASHED suffix added mechanically. OLD_PASSWORD and HASHED/MUST_CHANGE/UNLOCK combinations require the statement-specific semantic checks
- `password_hash`: SQL Server-compatible binary hash literal for an existing login migration; enforce version/format and CHECK_POLICY restrictions
- `sid_value`: binary SID literal. SQL-authenticated login SID uses the SQL Server 16-byte format; contained-user SID has its own documented format. Do not import Azure SQL login SID prefixes or Fabric SID/TYPE forms. SID is not a Windows contained-user option
- `object_id`: Microsoft Entra object-ID GUID string. SQL Server 17.x supports the OBJECT_ID extension, but the server must have working Arc-enabled Entra authentication and directory prerequisites
- `identity_name`, `secret`: credential identity and secret string contents, with an explicitly selected external resource/provider contract. They are not permission to use Azure SQL/Fabric-only identity modes on standalone SQL Server. For ALTER credentials, omitted SECRET clears the existing secret
- `account_name`: SQL Server service account string used by the documented service-master-key recovery forms; account/platform support is an external prerequisite
- `file_path`, `private_key_path`, `provider_library_path`: paths on the SQL Server host or supported network locations, accessed in the server/service security context. They are not paths on a SQL client by default. Certificate/private-key formats, file existence, permissions and provider signature/GUID must match the operation
- `blob_url`: Azure Blob Storage backup URL with an appropriate preexisting credential/access configuration. BACKUP/RESTORE MASTER KEY and SYMMETRIC KEY support this on SQL Server 2022+; this does not authorize `SERVER AUDIT TO URL`
- `certificate_subject`: subject string with the documented platform limit (64 characters on Linux, 128 on Windows). `date_value`: certificate validity date string accepted by SQL Server; prefer an unambiguous date representation and validate chronological relationships
- `certificate_binary`: ASN-encoded certificate binary literal. `private_key_binary`: private-key bytes in the supported import format. `signature_binary`: correctly computed hexadecimal signature blob, either module signature or enclave-enabled column-master-key signature according to the statement. These byte strings are not interchangeable
- `key_source_phrase`, `identity_phrase`: deterministic symmetric-key source/identity phrase strings. Both can be security-sensitive derivation material, not descriptive labels
- `provider_key_name`: key name in the registered external provider. `CREATE_NEW` and `OPEN_EXISTING` have real key-creation/mapping consequences. Provider algorithm/key-name support is not inferred from the SQL grammar
- `key_store_provider_name`, `key_path`: Always Encrypted client key-store provider identifier and opaque provider-specific key path. The column-master-key object stores metadata, not the external private key
- `algorithm_name`: key-store-provider encryption algorithm string for a column encryption key value. The built-in system providers require `RSA_OAEP`; arbitrary cryptographic algorithm names are not valid by default. Custom providers define their accepted identifiers
- `encrypted_value_binary`: externally generated encrypted column encryption key blob. One or two values are allowed, associated with distinct appropriate master keys. The engine/driver must check blob length, key consistency and provider support
- `audit_guid`: GUID string used to bind restored audit specifications to an audit. `size_value`: integral audit-file size in the chosen unit, with documented bounds. `file_count`: nonnegative/positive integral count as allowed by that option. `queue_delay_value`: 0 for synchronous delivery or a valid integer delay of at least 1000 milliseconds, at most 2147483647. These are constants, not arbitrary expressions
- `cookie_variable`: a declared local `@`-prefixed varbinary variable suitable for the EXECUTE AS/REVERT cookie; its value must correspond to the context being reverted. Do not treat NO REVERT as a context with a usable revert cookie
- `label`, `label_id`, `information_type`, `information_type_id`: sensitivity-classification string contents; IDs are not forced to a GUID-only type. Classification writes metadata and neither encrypts nor masks data

## Opaque expression/catalog nodes: genuinely partial coverage

- `predicate_argument_expression`: one RLS predicate-function argument, normally a target-table column or a context-permitted scalar argument. Lists are structurally represented, but expression grammar, function arity/types, correlation and dependency rules are not parsed. No statement terminators or nested statement text
- `audit_predicate_expression`: SQL Server audit event-filter predicate, not an ordinary unrestricted WHERE predicate. Resolve permitted event fields, comparison/literal types and Boolean combinations against CREATE/ALTER SERVER AUDIT documentation. Apply the documented exclusions for event fields. No subqueries, arbitrary SQL functions, or comma-separated SQL clauses. The two audit statements do not claim that all ordinary SELECT expressions are allowed
- `server_audit_action_group`, `database_audit_action_group`: single unquoted SQL Server 17.x audit group keyword from the appropriate catalog, not an arbitrary identifier or comma-containing list. Group availability is version/platform specific; do not import Azure-only groups such as LEDGER_OPERATION_GROUP merely because they appear on the shared page. The seven individual database actions are enumerated, but the action-group catalogs remain opaque. Source: [SQL Server audit action groups and actions](https://learn.microsoft.com/en-us/sql/relational-databases/security/auditing/sql-server-audit-action-groups-and-actions?view=sql-server-ver17)
- `permission_name`: one SQL Server 17.x permission keyword phrase valid for the selected scope/securable, with no commas, column parentheses, ON/TO/FROM clause, or statement boundary. The surrounding grammar owns lists, target scope, columns and principals. The full permission catalog is not enumerated. EXTERNAL LANGUAGE and EXTERNAL MODEL are included as named securable classes; the documented example permissions are EXECUTE EXTERNAL SCRIPT and EXECUTE, respectively. Per-class pages linked by the [GRANT reference](https://learn.microsoft.com/en-us/sql/t-sql/statements/grant-transact-sql?view=sql-server-ver17) remain authoritative
- `ALL [ PRIVILEGES ]` is an explicit historical fixed subset, not an expansion to all permissions. Column permission lists and object-target column lists must obey the documented permission-to-column rules. Reject incompatible double column-list specifications rather than letting an opaque permission token hide them

## Structured local nodes are not opaque inputs

`login_option`, `windows_login_option`, `password_option`, `limited_user_option`, `contained_user_option`, `contained_windows_user_option`, `user_option`, `application_role_option`, `certificate_date_option`, `private_key_source`, `private_key_password_option`, `asymmetric_key_source`, `provider_key_option`, `symmetric_key_option`, `key_encryptor`, `column_key_value_definition`, `security_predicate_definition`, `security_predicate_action`, `block_operation`, `security_policy_option`, `server_audit_option`, `audit_target`, `audit_file_option`, `audit_specification_add`, `audit_specification_action`, `database_audit_item`, `database_audit_action`, `object_permission`, `securable_class`, `authorization_class`, `key_decryptor`, `signature_module_class`, `signature_definition`, `signature_key`, and `sensitivity_option` are defined within their files. Consumers must expand these nodes, not output the node names literally. Definitions with the same local name in different files may differ.

Option lists express genuine lists, not permission to repeat contradictory options. Each ordinary setting occurs at most once. ALTER LOGIN password flags permit at most one MUST_CHANGE and one UNLOCK. CREATE SYMMETRIC KEY requires an ALGORITHM for a database-generated key; provider-derived forms have provider-specific requirements. Credential mappings, audit actions, columns and signatures likewise need identity and duplicate checks.

## Coverage and source discrepancies

- The external-language/model class spellings are directly documented in [CREATE EXTERNAL LANGUAGE permission examples](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-external-language-transact-sql?view=sql-server-ver17) and [CREATE EXTERNAL MODEL permission examples](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-external-model-transact-sql?view=sql-server-ver17). They use the common GRANT/DENY/REVOKE securable-class structure; accepting a class does not make every permission valid for it

- Certificates include separate DER/private-key and documented PFX example branches. CREATE/BACKUP CERTIFICATE reference diagrams omit some options shown by their own PFX examples. These files remain partial instead of asserting that all PFX combinations are implemented
- CREATE ASYMMETRIC KEY includes mainstream RSA import/generation/EKM structures, but RSA-HSM_2048/RSA-HSM_3072 mentioned in provider prose remain an explicit gap. RSA_512/RSA_1024 and older symmetric ciphers require lower database compatibility levels and are not generated for 170; they are not declared removed from the entire engine
- ALTER SECURITY POLICY structures add/alter/drop operations and state/replication changes. Operation-specific DROP BLOCK variants absent from the official syntax diagram are not claimed; predicate argument expressions remain partial. SCHEMABINDING must be changed by recreating the policy
- ALTER DATABASE SCOPED CREDENTIAL's live MicrosoftDocs file has an inconsistent monikerRange while its applies-to include names SQL Server. The implemented unchanged IDENTITY/SECRET shape is corroborated by the SQL Server credential pages; this source metadata problem is recorded in the inventory, not interpreted as removal of the SQL Server statement
- There is no standalone ALTER COLUMN MASTER KEY, CREATE/DROP SERVICE MASTER KEY, RESTORE CERTIFICATE, BACKUP/RESTORE ASYMMETRIC KEY, or OPEN/CLOSE CERTIFICATE/ASYMMETRIC KEY grammar in this inventory. Corresponding documented create/alter/import procedures are identified in the inventory

## Platform, edition and execution prerequisites

- Windows log audit targets require Windows; Linux uses file audit targets. SERVER AUDIT URL/EXTERNAL_MONITOR, OPERATOR_AUDIT and RETENTION_DAYS are excluded as Azure-specific
- Arc-enabled SQL Server Entra login/user support is included. Azure Arc-dependent Entra authentication is unsupported in SQL Server containers according to the SQL Server 2025 Linux feature matrix; presence of an EXTERNAL PROVIDER branch does not guarantee configuration availability
- Ordinary Always Encrypted is supported on SQL Server Linux, but Always Encrypted with secure enclaves is not. Consequently ENCLAVE_COMPUTATIONS is a Windows/platform-gated branch
- EKM requires a supported edition, a registered compatible provider and server configuration. Generic third-party EKM is not supported on Linux; Azure Key Vault EKM is the documented exception. Do not treat a Windows DLL path as a generally portable Linux provider path
- TDE, certificate imports, native compilation, service accounts, file I/O and external credential use have independent platform/edition/containment requirements. Certificate/asymmetric-key logins are for code signing and do not establish normal authentication sessions
- Open keys are session-bound; impersonation does not automatically close them. FORCE master-key operations can leave encrypted data unrecoverable. REMOVE PROVIDER KEY also affects the provider's external key. Dropping encryption metadata is not evidence that data decryption has completed

Platform references: [SQL Server 2025 Linux editions and components](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-editions-and-components-2025?view=sql-server-ver17), [Extensible Key Management](https://learn.microsoft.com/en-us/sql/relational-databases/security/encryption/extensible-key-management-ekm?view=sql-server-ver17). Each SNF file carries its statement reference as the first line.
